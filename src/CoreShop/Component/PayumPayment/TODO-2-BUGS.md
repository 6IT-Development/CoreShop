## Models

### B-01 — (reproduced, dependent) `setValues()` / `setValue()` with an `o_`-prefixed key calls a method that does not exist → `Error` instead of the intended compatibility mapping
- **Where:** used by `Model/GatewayConfig.php:30` and `Model/PaymentSecurityToken.php:31` (`use SetValuesTrait`). Root cause: `Component/Resource/Model/SetValuesTrait.php:34-40`.
- **Problem:** the `elseif` checks `method_exists($this, 'set' . preg_replace('/^o_/', '', $key))`, but then calls `$this->$method($value)` with the **unstripped** `$method` (`'set' . $key`). Reproduced: `(new GatewayConfig())->setValues(['o_factoryName' => 'paypal'])` → `Error: Call to undefined method ...GatewayConfig::seto_factoryName()`. The whole compatibility branch can never work; it only turns a silent no-op into a fatal error. Same for every CoreShop resource using the trait.
- **Fix:** in the trait, compute `$stripped = 'set' . preg_replace('/^o_/', '', $key)` and call that; add a unit test. (Fix in `Component/Resource`; tracked here because both models of this component expose the trait.)

### B-02 — (reproduced) `PaymentSecurityToken` allows mass assignment of `hash`, `targetUrl`, `afterUrl` and `gatewayName` through `setValues()` — (security hardening)
- **Where:** `Model/PaymentSecurityToken.php:31` (`use SetValuesTrait`), `:83-86` (`setHash()`), `:93-96` (`setTargetUrl()`), `:103-106` (`setAfterUrl()`), `:113-116` (`setGatewayName()`).
- **Problem:** the token is a bearer credential: whoever knows `hash` can drive the capture / authorize / notify flow, and Payum redirects to `targetUrl` / `afterUrl`. Because the class implements `ResourceInterface`, it must offer `setValues(array)`, and the trait maps **any** array key to a setter. Reproduced: `setValues(['hash' => 'attacker', 'targetUrl' => 'https://evil'])` rewrites both. No route exposes the resource today (no `routing` for `payment_security_token`, `Configuration.php` only registers a `ResourceController` class), so this is hardening: the first generic resource endpoint, import, or `ResourceController::addAction()` on this resource becomes an open redirect / token fixation vector.
- **Fix:** override `setValues()` / `setValue()` in `PaymentSecurityToken` to throw (`\LogicException('Payment security tokens are immutable through setValues().')`), or implement them with an explicit allow-list (only `details`). Make `hash` write-once (`setHash()` throws when a hash is already set and differs; Payum itself never calls `setHash()` after creation). Do not register admin routes for this resource (document it in `PayumPaymentBundle/DependencyInjection/Configuration.php`).

### B-03 — (plausible) Security tokens never expire and are never cleaned up; abandoned capture tokens and all notify tokens stay valid forever
- **Where:** `Model/PaymentSecurityToken.php` (no creation timestamp), `PayumPaymentBundle/Resources/config/doctrine/model/PaymentSecurityToken.orm.xml` (no time column / index). **(dependent)** no maintenance task or command anywhere in `src/CoreShop` touches `coreshop_payment_security_token`.
- **Problem:**
  - Payum only deletes a token in `HttpRequestVerifier::invalidate()`, i.e. after a **completed** capture / authorize / done request. A shopper who leaves the PSP page, closes the browser, or hits a gateway error leaves the capture **and** after-tokens behind. Notify tokens (IPN) are long-lived by design.
  - These rows are valid bearer tokens without any age limit: a leaked URL (browser history, proxy / access logs, `Referer`) stays usable for that payment indefinitely, and the table grows by at least two rows per checkout attempt.
  - The model has no field that would allow a safe purge (the `details` identity points to a payment, but there is no creation time).
- **Fix:** add `protected \DateTimeImmutable $createdAt` (set in the constructor; mapped as `datetime_immutable`, indexed) plus a migration that backfills `NOW()`. Add a Pimcore maintenance task / `coreshop:payum:purge-tokens --older-than=P30D` command that deletes capture / authorize / after tokens older than the threshold and notify tokens whose payment is in a final state (**dependent**, PayumBundle). Optionally reject tokens older than N days in a decorated `HttpRequestVerifier`.

### B-04 — (plausible) `PaymentSecurityToken::getId()` always returns `null`, so generic resource code treats every stored token as "not persisted"
- **Where:** `Model/PaymentSecurityToken.php:63-66`. Contract: `Component/Resource/Model/ResourceInterface.php:27` (`getId(): int|string|null`, the docblock explicitly allows string identifiers). Mapping: `PayumPaymentBundle/Resources/config/doctrine/model/PaymentSecurityToken.orm.xml:5` (`hash` is the identifier).
- **Problem:** the identifier is `hash`, but `getId()` hides it. Any generic CoreShop code that uses `getId()` — `ResourceController::addAction()` / `cloneAction()` (`$this->repository->find($resource->getId())` after flush, `ResourceBundle/Controller/ResourceController.php:165`), resource events / listeners that log or route by id, serializer metadata keyed on `id` — gets `null` and either loads nothing or treats the token as new. Already mentioned as a typing nit in `PayumPaymentBundle/TODO-3-IMPROVEMENTS.md` **I-08**; listed here because it is a contract violation with behavioural effect, not only typing.
- **Fix:** `public function getId(): ?string { return $this->hash; }` with a unit test; check `instanceof PaymentSecurityToken` callers for `null` assumptions (none found in `src/CoreShop`).

### B-05 — (plausible) The component's interface and mapping hardcode the concrete `GatewayConfig`, so the configurable `gateway_config` model can never be swapped — (dependent)
- **Where:** `Model/PaymentProviderInterface.php:25` (`setGatewayConfig(GatewayConfig $gatewayConfig)`), `:27-30` (`@return GatewayConfig`), `Model/PaymentProvider.php:28-38` (`?GatewayConfig`), `PayumPaymentBundle/Resources/config/doctrine/model/PaymentProvider.orm.xml:8` (`target-entity="CoreShop\Component\PayumPayment\Model\GatewayConfig"`), `PayumPaymentBundle/DependencyInjection/Configuration.php:56-69` (`resources.gateway_config.classes.model` is configurable). Callers that bypass the factory: `CoreBundle/Fixtures/Data/Demo/PaymentProviderFixture.php:60` (`new GatewayConfig()`).
- **Problem:** a project that configures its own `gateway_config` model (e.g. to add a `use_authorize` column, audit fields, or a fixed `encrypt()` from `PayumPaymentBundle` TODO-2 **B-02**) must extend this exact class, and even then the relation's `target-entity` points to the base mapped superclass, not to the configured entity, so Doctrine throws `MappingException` on schema update / hydration. There is no interface and no `resolve_target_entities` entry for gateway configs. `PayumPaymentBundle/TODO-2-BUGS.md` **B-08** covers the `payum.yml` side of the same problem; this is the model / mapping side.
- **Fix:** introduce `CoreShop\Component\PayumPayment\Model\GatewayConfigInterface extends \Payum\Core\Model\GatewayConfigInterface, ResourceInterface` (+ `CryptedInterface`), type `PaymentProviderInterface` against it (`setGatewayConfig(?GatewayConfigInterface): void`, `getGatewayConfig(): ?GatewayConfigInterface`), add an `interface` key to the `gateway_config` resource config so CoreShop registers `resolve_target_entities`, and point `target-entity` to the interface. Replace `new GatewayConfig()` in the fixture with the `coreshop.factory.gateway_config` factory (**dependent**).
