## Security

### C-01 — SQL injection through the JSON *keys* of the `orderState` report filter (reproduced)
- **Status:** fixed — keys are discarded via `Report/OrderStateFilter`; the states are bound as one `ArrayParameterType::STRING` list.
- **Where:** `Report/CategoriesReport.php:52-59,84-91`, `Report/ManufacturerReport.php:63-70,92-99`, `Report/ProductsReport.php:54-66,94-100,135-138`. Reached via `Controller/ReportsController.php:34-51` (`GET …/report/get-data`) and `:53-84` (CSV export).
- **Problem:** `orderState` is `json_decode($param, true)` from the request. The loop builds placeholder names from the array **keys**: `$orderStatePlaceholders[] = ':orderState' . $i;` and splices them directly into the SQL text (`… orderState IN (…)`). Only the *values* are bound; the keys are attacker-controlled. Passing a JSON object whose key contains SQL (for example a key that closes the `IN (...)` list and appends `OR (<subquery>) -- `) injects arbitrary SQL into the WHERE clause. I reproduced this against the real DBAL 3.10 `Parser` + `ExpandArrayParameters` pipeline (the exact code `fetchAllAssociative()` runs before handing the statement to PDO): the injected fragment survives into the final SQL string and the surplus named parameter is silently dropped, so the query executes. This yields a blind SQL injection usable to read arbitrary tables. Combined with C-02 it requires only any authenticated backend session; the CSV export is a GET, so a crafted URL opened by an admin also triggers it.
- **Fix:** never derive SQL from input keys. Normalise to a value list: `$states = array_values(array_filter((array) $decoded, 'is_string'));`, optionally intersect with the known order-workflow states, then bind as a single list parameter `orderState IN (:orderStates)` with `['orderStates' => $states]` and `ArrayParameterType::STRING`. Centralise this in one helper shared by the three reports (see TODO-3 **I-35**) and return HTTP 400 for non-list input.

### C-02 — Report, portlet and mutating admin endpoints have no server-side permission check
- **Status:** fixed — reports/portlets require `reports`; customer-transformer actions require the `coreshop_permission_ctc_assign_to_*` permissions; the solidifier and `removeStoreValuesAction` require `objects` plus the object ACL `save` on the product and every variant. `ConfigurationController` is left to ConfigurationBundle C-01.
- **Where:**
  - `Controller/ReportsController.php:34-84`, `Controller/PortletsController.php:34-83` — no permission check at all. Pimcore's own report controller requires `checkPermission('reports')` (`pimcore-source/bundles/CustomReportsBundle/src/Controller/Reports/CustomReportController.php:57`).
  - `Controller/CustomerTransformerController.php:34-245` — the `ctc_assign_to_new` / `ctc_assign_to_existing` permissions are declared (`DependencyInjection/Configuration.php:103-106`) but used only to hide menu entries (`Menu/MainMenuBuilder.php:340,350`). The `dispatch*` actions that **write** (move a customer into a company, reassign addresses) never check them.
  - `Controller/ProductVariantUnitSolidifierController.php:81-148` — `applyAction` rewrites unit definitions and quantity price rules of every variant and saves them; no permission check, no Pimcore object ACL check (`$variant->isAllowed('save')`).
  - `Controller/ProductController.php:31-48` — `removeStoreValuesAction` deletes product store values (prices). It is a `ResourceController` but never calls `isGrantedOr403()`, the product resource has no `permission`, and there is no object ACL check.
  - `Controller/ConfigurationController.php:31-76` — same gap; **already tracked** as ConfigurationBundle `TODO-1-CRITICAL.md` **C-01** (no permission check → RCE via wkhtmltopdf options). Not repeated; see C-03 for the CSRF angle.
- **Problem:** any authenticated backend user (even a restricted editor with no CoreShop/report rights) can read revenue/profit/customer PII, trigger C-01, restructure customer-company data, delete prices, and mass-overwrite variant pricing on objects they cannot otherwise edit.
- **Fix:** add `$this->checkPermission('reports')` (inherited from Pimcore `UserAwareController`) at the top of both report actions and the portlet actions (or a dedicated permission). In `CustomerTransformerController`, call `checkPermission('coreshop_permission_ctc_assign_to_*')` per action. In the solidifier and `removeStoreValuesAction`, call `checkPermission('objects')` plus `$object->isAllowed('save')` on the product and each variant. A `kernel.controller` listener using `checkActionPermission()` would make this robust for future actions.

### C-03 — Config save endpoint accepts GET/any method and double-encodes money/data — partially new, mostly dependent
- **Status:** fixed — `save-all` is restricted to POST (so the CSRF listener applies) and `get-all` to GET. The double-encoding stays with ConfigurationBundle B-02.
- **Where:** `Resources/config/pimcore/routing.yml:10-20` (`coreshop_admin_configuration_save_all` / `get_all` declare **no `methods:`**), `Controller/ConfigurationController.php:36-37`.
- **Problem:** `save-all` has no method restriction, so it answers GET as well as POST. Pimcore's CSRF listener (`admin-ui-classic-bundle` `CsrfProtectionListener::handleRequest`) returns early for cacheable (GET/HEAD) methods (`$request->isMethodCacheable()`), so a GET to `save-all` bypasses CSRF entirely; combined with C-02 (no permission check) this is a CSRF-write of global configuration. The `array_htmlspecialchars()` double-encoding of stored values is **already tracked** as ConfigurationBundle `TODO-2-BUGS.md` **B-02**.
- **Fix:** add `methods: [POST]` to both configuration routes (and to any other mutating CoreShop admin route lacking it — the customer-transformer dispatch routes already specify POST, good). Keep the permission check from C-02.

### C-04 — Auto-login after registration skips Symfony's login flow: no session-id migration (session fixation), no user checker, no login events
- **Status:** fixed — `CustomerLoginService` now calls `Security::login()` (`form_login` on `coreshop_frontend`, both overridable constructor arguments). Login is skipped when there is no request. The firewall name is still a default value, see TODO-2 B-02. No functional test was added.
- **Where:** `Customer/CustomerLoginService.php:32-36`, `EventListener/CustomerLoginListener.php:32-38`, `Resources/config/services/customer.yml:16-34`; caller `FrontendBundle/Controller/RegisterController.php:63` → `Customer/CustomerManager.php:112`.
- **Problem:**
  - `loginCustomer()` creates a `UsernamePasswordToken` and writes it straight to `security.token_storage`. Session migration happens only in `SessionStrategyListener` on `LoginSuccessEvent`, and this path never dispatches that event. So the session id from before registration becomes an authenticated session id. An attacker who can plant a session cookie (sibling subdomain, cookie injection) gets a logged-in session for the new account.
  - The path also skips `UserChecker::checkPreAuth/checkPostAuth`, `LoginSuccessEvent` and remember-me, so project hooks on login never run for registrations.
  - The firewall name `'coreshop_frontend'` is hard-coded (see TODO-2 **B-02**).
- **Fix:** inject `Symfony\Bundle\SecurityBundle\Security` and call `$security->login($user, 'form_login', $firewallName)`. Symfony 7.4's `Security::login()` runs the user checker, the authenticator manager, `LoginSuccessEvent` (session migration) and remember-me. Read the firewall name from configuration. Add a functional test that the session id changes on registration.

### C-05 — (dependent) The plaintext password of a newly registered user is serialized into the session; `User::eraseCredentials()` does nothing
- **Status:** fixed — `plainPassword` is now a blocked var and is never serialized. `CustomerManager` clears it after saving the user. `eraseCredentials()` is empty and has `#[\Deprecated]`. `setPlainPassword()` accepts `null`.
- **Where:** `Customer/CustomerManager.php:86-102` (`setPassword($userBackup->getPlainPassword())`, `plainPassword` stays set), `Customer/CustomerLoginService.php:34` (token holds that same object); `Component/User/Model/User.php:30` (`protected ?string $plainPassword`), `:46-51` (`eraseCredentials()`); Pimcore `models/DataObject/Concrete.php:674` / `Element/AbstractElement.php:642` (`__sleep()` serializes all non-blocked properties).
- **Problem:**
  - After registration the in-memory `User` still holds `plainPassword`. `CustomerLoginService` puts that instance into the token. At the end of the request `ContextListener` serializes the token into the session. Pimcore's `__sleep()` does not exclude `plainPassword`, so the cleartext password lands in the session store (files, Redis, DB) and stays there until the next request refreshes the user.
  - `eraseCredentials()` calls `Password::getDataForResource()` and throws away the result. It neither hashes the password nor clears `plainPassword`. Symfony also does not call it on this path, because the token is created by hand (C-04).
- **Fix:**
  - In `CustomerManager`, after saving the user, clear the plain password (add a `setPlainPassword(?string)` / `eraseCredentials()` that sets it to `null`).
  - In `Component/User/Model/User`, implement `__serialize()` / `__sleep()` without `plainPassword`. Make `eraseCredentials()` empty and mark it `#[\Deprecated]`; Symfony 7.3 deprecated it, and `AuthenticatorManager::checkEraseCredentials()` triggers a deprecation for a non-empty implementation on every form login.
  - Fixing C-04 alone is not enough.

### C-06 — (dependent, plausible) A customer's cart and address book stay reachable in the browser session after logout (multi-store), and the next person to log in takes over that cart with the previous customer's addresses
- **Status:** fixed — both logout listeners now remove the session lists of **all** stores. `SessionAndStoreBasedStorageListContext` (with the new optional `$customerContext`) drops a session list owned by a registered customer other than the current one; guest-owned lists are unaffected. `CartBlamerListener` no longer takes over another registered customer's cart.
- **Where:** `EventListener/ShopUserLogoutHandler.php:45-50`; `StorageListBundle/Core/EventListener/SessionStoreStorageListLogoutSubscriber.php:34-58`; `Component/StorageList/Core/Context/SessionAndStoreBasedStorageListContext.php:31-68`; `EventListener/CartBlamerListener.php:63-90`; `Checkout/Step/AddressCheckoutStep.php:57-71`; docs/config `invalidate_session: false` (`Resources/config/pimcore/security.yml:36`, `docs/01_Getting_Started/00_Installation.md`).
- **Problem:**
  - Logout keeps the session (`invalidate_session: false`). Both logout listeners remove only the cart key of the **current** store (`coreshop.cart.<storeId>`). Carts of other stores that share the session (same host, store selected by path/locale/domain alias) stay in the session.
  - `SessionAndStoreBasedStorageListContext` returns the session cart after checking only the store. It never compares `cart.customer` with the current (now anonymous) user.
  - The next visitor in that browser (shared or public computer) gets the previous customer's cart in store 2, with `customer` = the previous customer. `CustomerCheckoutStep::validate()` is true, so the checkout auto-forwards. `AddressCheckoutStep` treats the cart as non-guest (`$customer->getUser() !== null`). The address form then lists the previous customer's address book (`AddressChoiceType` → `CustomerAddressAllocator`), and an order can be placed in the previous customer's name.
  - If someone else logs in instead, `CartBlamerListener::blame()` sets `cart.customer` to the new user. It does not clear the shipping or invoice address (it only fills them when they are `null`), so the new customer's order keeps the previous customer's addresses.
- **Fix:**
  - On logout, remove every `coreshop.cart.*` key, or invalidate the session.
  - In the session cart context, throw `StorageListNotFoundException` when `cart.customer` is set and differs from the customer context (also when the visitor is anonymous).
  - In `CartBlamerListener`, do not take over a cart that belongs to another registered customer. When the customer changes, reset the addresses that belong to the previous customer.

## Data loss — product store values

### C-08 — Saving a variant that shows **inherited** store values moves the parent's price rows to the variant (parent loses its prices)
- **Status:** fixed — `StoreValues::copyStoreValues()` makes a real new copy: no id, no product, deep-copied unit-definition prices. `getDataFromEditmode()`, `save()` and `createDataCopy()` all use it. `getDataFromEditmode()` ignores a submitted id from another field or store. `save()` refreshes (reverts) the other product's managed record after breaking inheritance. No `ProductStoreValues::__clone()` was added, because Pimcore's DeepCopy calls `clone` on every nested object and would reset the ids in its own copies. Not verified against a DB, and no Behat test was added.
- **Where:** `CoreExtension/StoreValues.php:666-676` (`getDataFromEditmode()`: `find($storeValuesId)` then `clone $storeValuesEntity` – the clone keeps the parent's `id`), `:438-439` (`EntityMerger::merge()` in `save()`), `:467-486` (`persist` + global `flush()`). (dependent) `Component/Core/Model/ProductStoreValues.php` (no `__clone()`), `ResourceBundle/Doctrine/ORM/EntityMerger.php:62-90` (`registerManaged($entity, $id, $this->getData($managedCopy))`). Data source: `admin-ui-classic-bundle/src/Controller/Admin/DataObject/DataObjectController.php:642-730` (`getDataForField()` serves the **parent's** data when the child field `isEmpty()`), `Resources/public/pimcore/js/product/storevalues/builder.js:123-129` (always sends `id`), `Resources/config/serializer/Model.ProductStoreValues.yml:5-9` (`id` in `Detailed`).
- **Problem:**
  - A variant without own store values gets the parent's values in the admin, including the parent's row `id` per store. When the editor changes a price on the variant and saves, the whole field (all stores) is sent with those ids.
  - `getDataFromEditmode()` detects "belongs to another product" and clones, but `clone` copies `id` (verified: `clone` of a `ProductStoreValues` with id 42 has id 42 and shares the same `productUnitDefinitionPrices` collection instance – **(reproduced)** `clone.php`). `createDataCopy()` (`:380-393`) shows the intended behaviour: it resets `id`, `product` and `productUnitDefinitionPrices` via reflection; the edit-mode path forgot it.
  - In `save()`, `EntityMerger::merge()` finds the parent row by that id, removes it from the identity map and registers the **clone** as the managed instance of the parent's row. The product check at `:441` is now false (the clone already points to the child), so nothing breaks the link. `flush()` issues `UPDATE coreshop_product_store_values SET product = <child>, price = … WHERE id = <parent row>`.
  - Result: every store row of the parent (and its unit-definition prices, FK `product_store_values`) is moved to the variant. The parent and all other variants that inherit from it lose their prices (price 0 / not purchasable) in every store, silently.
  - Related path in `save()` itself (`:441-455`, "break the inheritance"): the inherited entity is merged into the main EM and modified, then a clone is persisted; the original managed (parent) entity stays dirty and is flushed too, so the parent's row is overwritten with the child's values. The clone is inserted without the unit-definition prices (they stay on the parent row).
- **(plausible):** traced end to end through Pimcore's `getDataForField()`, the JS builder, `getDataFromEditmode()`, `EntityMerger` and the UoW; not run against a DB (no SQLite/MySQL sandbox). **Verify:** parent P with a price in store 1, variant V empty → open V, change the price, save → `SELECT id, product FROM coreshop_product_store_values` before/after.
- **Fix:**
  - Add `ProductStoreValues::__clone()` that resets `id = null`, `product = null` and deep-copies `productUnitDefinitionPrices` (clone each price, `setProductStoreValues($this)`, reset its id). Then use it in `getDataFromEditmode()`, `save()` and `createDataCopy()` (drop the reflection code).
  - In `getDataFromEditmode()`, never trust a submitted id that belongs to another product/field: `if ($entity->getProduct()?->getId() !== $object->getId() || $entity->getFieldName() !== $this->getName())` → treat as new.
  - In `save()`, do not merge/persist entities that belong to another product; `detach`/`refresh` the parent's managed instance after cloning so its changes are not flushed.
  - Add a Behat/functional test: edit inherited store values on a variant, assert the parent rows are unchanged.

## Install / upgrade

### C-10 — `coreshop:install` marks every CoreBundle migration as executed, so pending migrations are skipped for good (including the two new ones)
- **Status:** fixed — `coreshop:install` marks the migrations only on a fresh install (no `coreshop_store` table before the run) when no step failed. Otherwise it leaves them pending and tells the admin to run `coreshop:migrate`. They are not run automatically, because several migrations are not idempotent (for example `Version20230711143927`, `Version20231201091924`) and would fail after a schema reset. `Installer::install()` no longer calls `parent::install()` (which marked them again); it only sets the SettingsStore flag. Admins who already have bogus rows still need `doctrine:migrations:version --delete`.
- **Where:** `Command/InstallCommand.php:79-98`, `Installer.php:61-64`. **(dependent)** `vendor/six-it/pimcore-source/lib/Extension/Bundle/Installer/SettingsStoreAwareInstaller.php` (`markInstalled()`), `ResourceBundle/Installer/PimcoreClassInstaller.php` (`createClass(..., $options[OPTION_UPDATE_CLASSES] ?? false)`), `Component/Pimcore/DataObject/ClassInstaller.php:46-62`.
- **Problem:**
  - `InstallCommand::execute()` always calls `$this->installer->markAllMigrationsInstalled()` at the end. This writes a `migration_versions` row for every `CoreShop\Bundle\CoreBundle\Migrations\*` class that is not executed yet. It does so unconditionally: also when a step failed (`$errored = true`), and also when the command runs against a database that already has CoreShop.
  - The `resources` step (`coreshop:resources:install --application-name coreshop`) runs **without** `--update-classes`. `ClassInstaller::createClass()` therefore skips classes that already exist. On an existing shop the class definitions are not updated and the migrations that would add the fields are marked as done.
  - Concrete effect on this branch: when `coreshop:install` runs on an existing shop (for example after an upgrade, or via `bundle:install` when the SettingsStore flag is missing, see C-11), `Version20260419121310` and `Version20260616120000` are recorded without running. `CoreShopUser.passwordResetHashCreatedAt` and `CoreShopOrder.lastActivatedAt` never get created. Then:
    - `OrderBundle/Pimcore/Repository/OrderRepository.php:107` (`setOrderKey(['lastActivatedAt', 'creationDate'])`) produces SQL with an unknown column. Every lookup of the customer's latest cart fails, so the storefront cart is broken.
    - `UserBundle/Pimcore/Repository/UserRepository.php:69` and `FrontendBundle/Controller/RegisterController.php:100,148` call accessors that do not exist on the generated class. The base `Order`/`User` stubs throw `ImplementedByPimcoreException`, so password reset breaks.
  - Recovery is not obvious. `doctrine:migrations:migrate` reports "already at latest version". The admin has to find the bogus rows and delete them with `doctrine:migrations:version --delete`.
- **Fix:** Call `markAllMigrationsInstalled()` only on a real fresh install, i.e. when `DatabaseSetupCommandsProvider` created the schema and the class installer created (not skipped) all classes. Never call it when `$errored` is true. On an existing install, run `coreshop:migrate` instead of marking. The alternative: run the resources step with `--update-classes` and let the (idempotent, `hasField`-guarded) migrations execute normally.

Fixtures: `Fixtures/Data/Application/ConfigurationFixture.php:60-62`, `ZoneFixture.php:55-61`, `AddressIdentifierFixture.php:50-58`, `CountryFixture.php:110-158,159-182,191-197`.
- **Problem:** `doctrine:fixtures:load --group application --append` runs again on every `coreshop:install`, including on an existing database. The application fixtures are not idempotent:
  - `ConfigurationFixture` resets every `system.*` key (`system.order.prefix`, `system.invoice.prefix`, `system.guest.checkout`, …) to the defaults. Customised document number prefixes silently go back to `O`, `IN`, `SH`, `Q`. Number ranges can then collide with historic numbers **(plausible)**.
  - `CountryFixture` overwrites the names (all languages), `addressFormat`, `salutations`, `zone` and `currency` of **every** existing country. It adds every country to the default store, and resets the default store's currency to EUR and its base country to AT (`:191-197`).
  - `ZoneFixture` and `AddressIdentifierFixture` insert new rows every run (no existence check, no unique constraint). Duplicate `shipping`/`invoice` identifiers make `AddressIdentifierRepository::findByName()` throw `NonUniqueResultException` (see `AddressBundle/TODO-2-BUGS.md` B-10) **(dependent)**. That method is used in checkout address handling.
  - `CountryFixture` creates the AT states again (no existence check at `:164-181`). That gives duplicate `coreshop_state` rows.
  - The path is reachable without interaction. `Installer::install()` (Pimcore `bundle:install CoreShopCoreBundle`) runs whenever `isInstalled()` is false. That is the case on every installation that predates the SettingsStore flag or where the flag was lost.
- **Fix:** Run `coreshop:install:fixtures` only after the tables were (re)created in the same run (return it from `setupDatabase()` together with `create-tables`, not from `getCommands()`). Also make each fixture idempotent: `findOneBy(['name' => …])` for zones and identifiers, a state existence check like `SetupStatesCommand`, and only set configuration keys that are `null` (`configurationService->get($key) === null`). Only set store currency and base country when they are empty.

### C-12 — `Version20241018060845` rewrites `config/bundles.php` with a hand-rolled serializer and can leave the application unbootable
- **Where:** `Migrations/Version20241018060845.php:30-38,40-68,70-86,88-101,103-111`.
- **Problem:**
  - `buildContents()` generates PHP by string concatenation. For a bundle with an empty env array (`Foo::class => []`, which is valid in `bundles.php`), `substr($contents, 0, -2)` removes the opening `[`. The result is `Baz\Qux::class =>],`, a parse error **(reproduced: `bundles.php` in repro → `PHP Parse error: syntax error, unexpected token "]"`)**. A broken `bundles.php` stops the kernel from booting, including `bin/console`. The admin cannot run `migrations:migrate down` to recover.
  - Even when it works, the rewrite drops all comments and any expressions (for example `class_exists(X::class) ? [...] : []` gets frozen to the evaluated value), and the formatting is rewritten.
  - The file is written from `up()`, so it is also written in `--dry-run` / `--write-sql` mode (see TODO-2 **B-65**). `down()` removes `CoreShopFrontendBundle` even if the project had it registered before the migration.
  - On read-only or immutable deployments (containers), `file_put_contents()` fails with a warning only. The migration is then still recorded as executed.
- **Fix:** Do not edit project configuration from a migration. Replace this with a console hint or a Pimcore/Flex recipe step (`$this->write('Enable CoreShopFrontendBundle in config/bundles.php')`). If it must stay: use `var_export()` for each env array, skip the write when the bundle is already registered (`return` before `dump()`), never write in dry-run (use the guard from TODO-2 **B-65**), and make `down()` a no-op.
