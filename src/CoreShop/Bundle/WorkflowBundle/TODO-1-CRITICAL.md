## Container build / configuration

### C-01 — The places and transitions of every CoreShop state machine are pushed into `framework.workflows` from `load()`. This only works because the bundle is registered before `FrameworkBundle`; in any other order every CoreShop workflow loses its places and transitions — (reproduced: current order works) (plausible: outage on reorder) (dependent)
- **Where:** `DependencyInjection/CoreShopWorkflowExtension.php:28-51` (`$container->prependExtensionConfig('framework', ...)` inside `load()`). Bundle order: `OrderBundle/CoreShopOrderBundle.php:78` (priority `3600`), `PaymentBundle/CoreShopPaymentBundle.php:44` (priority `1550`), vendor `six-it/pimcore-source/lib/Kernel.php:234-247` (`FrameworkBundle` at priority `100`), `six-it/pimcore-source/lib/HttpKernel/BundleCollection/BundleCollection.php` (sorted by priority, the highest priority of a bundle wins). Symfony: `vendor/symfony/dependency-injection/Compiler/MergeExtensionConfigurationPass.php` (extensions are loaded one by one in bundle order, each with its **already merged** config).
- **Problem:**
  - `prependExtensionConfig()` is meant for `PrependExtensionInterface::prepend()`, which runs for all extensions **before** any `load()`. Called from `load()`, it only adds to the `framework` config if the `framework` extension has **not been loaded yet**. `MergeExtensionConfigurationPass` loads extensions in bundle order, so the result depends on the bundle order.
  - Today it works by accident: the CoreShop bundles register `CoreShopWorkflowBundle` with priority 1550/3600, so it sorts before `FrameworkBundle` (100). Checked in `var/cache/dev/ContainerVKgrfLp/App_KernelDevDebugContainer.php:12701`: `coreshop_order` has its 5 places and transitions.
  - If the bundle is loaded after `FrameworkBundle` (plain Symfony kernel, a test kernel, a project that registers the bundle with a lower priority and no CoreShop bundle that raises it, or a future change of the Pimcore priorities), `framework.workflows.coreshop_*` only has `type`/`marking_store`/`supports` from `OrderBundle/Resources/config/pimcore/workflow/*.yml`. Every state machine is then built without transitions. `coreshop_order_sales_type` `order` can no longer be applied, so checkout cannot commit an order, and the order admin shows no transitions. There is no error at build time.
  - The same `load()` also sets `coreshop.state_machines`, `.callbacks` and `.colors`, which is fine there; only the `framework` prepend is wrong.
- **Fix:**
  - Implement `PrependExtensionInterface` (or move to `AbstractBundle::prependExtension()`, TODO-3 **I-02**). In `prepend()`, read the raw configs with `$container->getExtensionConfig('core_shop_workflow')`, resolve parameters, run `processConfiguration()` with `Configuration`, and prepend `framework.workflows.<name>.places/transitions` there. Keep the parameters in `load()`.
  - Note that other bundles also contribute `core_shop_workflow` config through Pimcore's `Resources/config/pimcore/*.yml` auto-loading. Check that these files are already in the extension configs when `prepend()` runs (they are loaded by the kernel before the compiler passes, so they should be).
  - Add a functional test that boots a kernel with `FrameworkBundle` registered **before** `CoreShopWorkflowBundle` and asserts that `state_machine.coreshop_order` has the `create` transition.
