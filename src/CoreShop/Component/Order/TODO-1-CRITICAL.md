## Money charged wrongly

### C-01 — (verified) Credit vouchers can be spent again and again: `VoucherModifier::increment()` overwrites `creditUsed` instead of adding to it
- **Where:** `Modifier/VoucherModifier.php:62-64` (`setCreditUsed(-1 * $item->getDiscount(true))`). Compare `decrement()` at `:123-125` (`getCreditUsed() - …`, i.e. a running total) and the consumer `Component/Core/Cart/Rule/Action/VoucherCreditActionProcessor.php:81-84` (`creditAvailable - creditUsed`). `Model/CartPriceRuleVoucherCode.php:143-151` only offers a plain setter.
- **Problem:** with a 100.00 credit code: order 1 uses 60 → `creditUsed = 60` (40 left); order 2 uses 40 → `creditUsed = 40` (should be 100) → 60 left again; order 3 uses 60 … The code never runs out, which is real money lost. Cancelling an order then subtracts from the wrong base (`max(0, 40 - 60) = 0`), making it worse. `features/domain/cart/rules/voucher_credit_action.feature` never places two orders with the same code.
- **Fix:** accumulate: `setCreditUsed($voucherCode->getCreditUsed() + $used)`, clamped to `creditAvailable`. Better: add `addCreditUsed(int)` / `subtractCreditUsed(int)` (clamped at `>= 0`) to `CartPriceRuleVoucherCode(Interface)` and use them in both paths. Convert the amount into the credit currency first (**C-02**). Make it race-safe (**C-09**). Add a test with two orders + one cancellation on the same credit code.

### C-02 — (verified, dependent) Amount-based cart rules and credit vouchers are converted into the shopper's currency, but the cart is calculated in the store base currency
- **Where:** `Component/Core/Cart/Rule/Action/DiscountAmountActionProcessor.php:75-85`, `Component/Core/Cart/Rule/Action/SurchargeAmountActionProcessor.php:73-77`, `Component/Core/CartItem/Rule/Action/DiscountAmountActionProcessor.php:81-85` (all convert to `$cart->getCurrency()`), `Component/Core/Cart/Rule/Action/VoucherCreditActionProcessor.php:57-62`, `:83`; credit booking in `Modifier/VoucherModifier.php:63`. Context: `Cart/CartContextResolver.php:30` provides `base_currency`; `Component/Core/Order/Processor/CartCurrencyConversionProcessor.php:39-60` converts to the shopper currency afterwards.
- **Problem:** all cart amounts (`getTotal`, `getSubtotal`, adjustments, `PriceRuleItem` discount) are in base currency until the conversion processor runs. Product, shipping and payment rule actions correctly convert into `$context['base_currency']` (e.g. `Component/Product/Rule/Action/DiscountAmountActionProcessor.php:41,52`); the cart-rule amount actions convert into the **shopper** currency and then apply that number as a base amount. Example: store EUR, shopper picks HUF (1 EUR ≈ 400 HUF), rule "10 EUR off" → ~4000 EUR discount, capped only by the cart value → the cart becomes free. Surcharges are distorted the same way. The credit action takes `min()` of a base-currency total and a credit-currency amount; `VoucherModifier` stores a base-currency discount in a credit-currency field. Shoppers choose the currency (even inactive ones, see `FrontendBundle/TODO-2-BUGS.md` **B-17**), so this is exploitable.
- **Fix:** resolve the context with `CartContextResolverInterface` and convert into `$context['base_currency']` in all cart / cart-item amount actions. In the credit action convert the remaining credit to base currency before `min()`; in `VoucherModifier` convert the booked discount back into `creditCurrency`. Add a behat scenario with a non-base cart currency.

### C-03 — (verified, dependent) Stacked cart-level percentage discounts can make the cart total negative; the payment step is then skipped
- **Where:** `Component/Core/Cart/Rule/Applier/CartRuleApplier.php:83-91` (cap `min($discount, Σ item->getTotal($withTax))`, discounts only; surcharges uncapped), `Component/Core/Cart/Rule/Action/DiscountPercentActionProcessor.php:57-63` (base = `getSubtotal()`), `Model/Order.php:324-330` (total = subtotal + non-neutral adjustments, no clamp). `Component/Core/CartItem/Rule/Applier/CartItemRuleApplier.php:75-86` already handles this case for item rules.
- **Problem:** cart rules only write *neutral* adjustments to items (`CartRuleApplier.php:219-225`), so item totals and the subtotal never shrink between rules, and each rule is capped at the full cart value. Automatic 50 % + voucher 60 % on a 100.00 cart → total −10 (+ shipping). `PaymentCheckoutStep::isRequired()` returns `total > 0` (`CoreBundle/Checkout/Step/PaymentCheckoutStep.php:48-51`) and `Checkout/DefaultCheckoutManagerFactory.php:43-45` drops the step, so the order is committed with a negative total, voucher usage is incremented and stock is reserved. `discount_over_100_percent.feature` declares two vouchers but applies only one.
- **Fix:** in `CartRuleApplier::apply()` cap against the *remaining* value per item (`getTotal($withTax) + getNeutralAdjustmentsTotal(CART_PRICE_RULE, $withTax)`), as `CartItemRuleApplier` does, and distribute over the remaining amounts. Add a final safety clamp so `Order::getTotal()` can never be < 0 (or block checkout). Add a behat test with two stacked percentage vouchers.

### C-04 — (verified, dependent) A unit price goes negative when a product discount is larger than the price
- **Where:** `Calculator/PurchasablePriceCalculator.php:53-55`; same pattern in `Component/Product/Calculator/ProductPriceCalculator.php:46-48` (the path products actually take). `Component/Product/Rule/Action/DiscountAmountActionProcessor::getDiscount()` returns the configured amount without capping it at the price.
- **Problem:** `$price -= $discount` has no lower bound. Product price rule "10.00 off" on a category that contains a 5.00 item → item price −5.00. It flows through `CartItemsProcessor` into item total, subtotal and order total; the order is under-charged and totals can go negative. No later processor clamps it.
- **Fix:** `$price = max(0, $price - $discount)` in both calculators, or cap the discount at `$price` in the composite discount calculator / amount action. Add a unit test.

### C-05 — (reproduced, dependent) Invoices (and shipments) drop item-level cart rule discounts, so the invoice total is higher than what was charged
- **Where:** `Transformer/OrderItemToInvoiceItemTransformer.php:66-70` (`setTotal($orderItem->getItemPrice(...) * $quantity)`), `Transformer/OrderItemToShipmentItemTransformer.php:65-69`, `Transformer/OrderToInvoiceTransformer.php:165-182`, `:212-229`. Discount origin: `Component/Core/CartItem/Rule/Applier/CartItemRuleApplier.php:165-172` (non-neutral adjustment on the item) and `Cart/Rule/Action/CartItemActionProcessor.php:112-120` (same amount on the order as **neutral**). `Model/AdjustableTrait.php:172-190`, `:212-226` exclude neutral adjustments from totals.
- **Problem:** with an `order_item_action` rule ("10 % off category X"), the order item total is 90 and `order.total` is 90 + shipping. The invoice item is `itemPrice × qty = 100`, and `calculateAdjustments()` reads `$order->getAdjustmentsTotal('cart_price_rule')`, which skips neutral adjustments → 0. The invoice shows 100 + shipping. Additionally `createWithData(..., $adjustment->getNeutral())` (`:177`) copies the neutral flag of the *first* adjustment of a type, so an ordinary cart discount can end up neutral on the invoice and vanish from its total. `getProcessedAdjustmentValue()` (`:220-225`) also counts neutral adjustments, so later invoices never pick up the lost amount.
- **Fix:** derive document item amounts from the order item total (`getTotal()` / `getConvertedTotal()`), prorated by quantity (see **C-06**), or copy the order item's non-neutral adjustments onto the document item. In `calculateAdjustments()` iterate over non-neutral adjustments only, always create them non-neutral, and make `getProcessedAdjustmentValue()` skip neutral ones. Add an invoice test with an item-level cart rule.

### C-06 — (reproduced) Invoice item totals are re-derived from rounded unit prices, so a fully invoiced order does not sum to the order total
- **Where:** `Transformer/OrderItemToInvoiceItemTransformer.php:66-70`. Compare `Component/Core/Order/Processor/CartItemProcessor.php:70-88` (gross store), `:98-116` (net store), `CartCurrencyConversionProcessor.php:58-63`.
- **Problem:** the order item computes `total = round(unit × qty)` and taxes the whole line. The invoice uses `itemPriceNet × qty` / `itemPriceGross × qty`, where the unit net / gross price already carries per-unit tax rounding. Reproduced: gross store 19 %, unit 4999 × 10 → order net 42008, invoice net 42010; net store 20 %, unit 417 × 7 → order gross 3503, invoice gross 3500. In B2B (net) stores the payable invoice gross differs from the amount charged; in gross stores net and VAT on the legal document are wrong. Same for converted totals.
- **Fix:** document item total = `round(orderItem->getTotal($withTax) × qty / orderedQty)` (and converted), with the document that completes the item's quantity taking the remainder, so Σ invoices = order exactly. Add a unit test with the two examples above.

### C-07 — (verified, dependent) Fractional quantities of normal products are accepted and priced pro rata
- **Where:** `Component/Core/Order/Modifier/CartItemQuantityModifier.php:46-48` (only `0 >= $target` rejected, before rounding), `:78-80` (no unit definition → returned unrounded); `OrderBundle/Form/Type/QuantityType.php`, `CoreBundle/Form/Extension/QuantityTypeExtension.php` (`step: 1` is client-side only; `NumberType` without `scale`); `Component/Core/Order/Processor/CartItemProcessor.php:81,109` (`round($itemPrice * $quantity)`).
- **Problem:** posting `quantity=0.01` for a product without unit definitions stores 0.01; the line costs 1 % of the price and the order is created with a fractional physical item. No server-side constraint applies (dead `validation/CartItem.yml`, `OrderBundle/TODO-2-BUGS.md` **B-31**; `GreaterThan(0)` would not block 0.01 anyway). With unit precision 0, `0.4` passes the `0 >=` check and is rounded to `0.0` → a zero-quantity line although `allowZeroQuantity` is false.
- **Fix:** in `CartItemQuantityModifier::modify()` round first (precision = unit precision, or 0 without unit definition / when fractional sales are not allowed), then reject `<= 0` (`< 0` with `allowZeroQuantity`) and non-finite values. Add a server-side `Type` / `DivisibleBy` constraint on the quantity form field.

### C-08 — (reproduced, dependent) `ProportionalIntegerDistributor` throws `DivisionByZeroError` when the weights sum to 0, which breaks the cart permanently
- **Where:** `Distributor/ProportionalIntegerDistributor.php:28-33`. Callers: `Component/Core/Shipping/Taxation/TaxCalculationStrategyCartItems.php:63-69`, `Component/Core/Cart/Rule/Applier/CartRuleApplier.php:97,170-171`.
- **Problem:** `$total = array_sum($integers)` is never checked. Reproduced: `distribute([0], 500)`, `distribute([0,0], 100)`, `distribute([100,-100], 10)` → `DivisionByZeroError`; `distribute([], 100)` → "Undefined array key 0" warnings and garbage. Real path: carrier with the `cartItems` shipping-tax strategy, shipping > 0, and the only taxable items total 0 (gift items forced to 0 by `CartItemsProcessor`, free samples, 100 % discounted item) → `collectCartItemsTaxRules` returns `[ruleId => 0]`, passes the `!$totalAmount` guard, and `distribute([0], shipping)` throws. `DivisionByZeroError` is an `Error`, not an `Exception`, so it escapes the processor chain (`CartManager::persistCart`): every recalculation (even "remove item") returns 500 until the cart expires. Same crash in `CartRuleApplier` for a surcharge with `includeNonDiscountableItems` on zero-total items.
- **Fix:** guard `$total === 0` (equal split via `IntegerDistributor`, or all zeros; document it in the interface), assert non-empty input, and let callers skip distribution when the weight sum is 0. Add unit tests (see TODO-3 **I-21**).

## Security / data integrity

### C-09 — (plausible, dependent) Voucher usage limits and credit are not race-safe (check-then-act plus lost-update increment)
- **Where:** `Cart/Rule/Condition/VoucherConditionChecker.php:57-78` (checks `uses >= max`), `Modifier/VoucherModifier.php:57-60`, `:62-64`, `:80-92` (read-modify-write, run from the `create` transition callback, `OrderBundle/Resources/config/pimcore/workflow/coreshop_order.yml:43-46`, after `OrderCommitter` persisted the order).
- **Problem:** validation runs during cart recalculation / `doCheckout`; the counter is bumped later with `setUses(getUses() + 1)` on an entity loaded earlier, without lock, version or atomic UPDATE. Two concurrent checkouts with a single-use code (or a per-customer limit of 1) both pass and both write `uses = 1` → the code is used twice, counted once, and usable a third time. Same for `creditUsed` (**C-01**) and the per-customer `CartPriceRuleVoucherCodeCustomer` row: an insert race creates two rows, after which `findUsesByCustomer()` (`getOneOrNullResult()`) throws `NonUniqueResultException` for that customer forever.
- **Fix:** take a Symfony Lock keyed on the voucher code from re-validation through commit, or perform conditional atomic updates inside the commit transaction (`UPDATE … SET uses = uses + 1 WHERE id = :id AND (:max = 0 OR uses < :max)`, `credit_used = credit_used + :amt WHERE credit_used + :amt <= credit_available`) and fail the checkout when 0 rows are affected. Add a unique index on (`voucherCode`, `customerId`) in `CartPriceRuleVoucherCodeCustomer.orm.xml`.
