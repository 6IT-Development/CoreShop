## Data written wrongly / area-wide errors

### C-01 — Restoring a product version (or recycle-bin entry) turns `nested` conditions into plain arrays; the saved rule then throws a `TypeError` on every price calculation for that product — (serializer round trip verified, runtime path plausible) (dependent: Component/Rule, ProductBundle, ProductQuantityPriceRulesBundle)
- **Where:**
  - `Resources/config/serializer/Model.Condition.yml:18-21` (and `Model.Action.yml:18-21`): `configuration` is serialized as `type: array` with no inner type.
  - A `nested` condition stores its children as `Condition` **objects** inside the `configuration` array (`OrderBundle/Form/Type/Rule/Condition/NestedConfigurationType.php` and the Product/Payment/Shipping/QuantityPrice copies add `conditions` as a `…ConditionCollectionType` whose entries have `data_class` = `Condition`; the column is the PHP-`serialize()`d DBAL `array` type, `Resources/config/doctrine/model/Condition.orm.xml:12`).
  - `ProductBundle/CoreExtension/ProductSpecificPriceRules.php:201-253` and `ProductQuantityPriceRulesBundle/CoreExtension/ProductQuantityPriceRules.php:203-257` store the rules in Pimcore versions and recycle-bin data via JMS (`toArray()` / `fromArray()`, group `Version`), using this bundle's metadata for `Condition`.
  - Run against the vendored `jms/serializer` 3.32.9 with this bundle's metadata: a `nested` `Condition` whose configuration holds a child `Condition` serializes the child to an array, and `fromArray(..., Condition::class)` returns `configuration['conditions'][0]` as `array`, not `Condition` (verified, script: create outer/inner `Condition`, `toArray` + `fromArray` with group `Version`).
  - `Component/Rule/Condition/NestedConditionChecker.php`: `isValid($subject, $rule, [$condition], $params)` → `RuleConditionsValidationProcessor::isConditionValid(..., ConditionInterface $condition, ...)` → `TypeError` for an array.
- **Impact:**
  - "Publish" of an older product version, restore from the recycle bin, or publishing a draft that was written by `marshalVersion()` goes through `unmarshalVersion()` and then `save()`: the arrays are merged into the managed rule and flushed, so the database now holds a nested condition whose children are arrays.
  - From then on every price calculation for that product (product page, listing, cart, checkout, order creation) throws `TypeError` → HTTP 500, until the rule is opened and re-saved in the admin. Specific price rules with `nested` conditions are common (e.g. "customer group AND country").
  - The same arrays are returned when the admin shows a version preview; this is harmless there, but it hides the problem from editors.
- **Fix:**
  - Short term (in this bundle): add a JMS `serializer.post_deserialize` subscriber (or a custom handler for `Condition::configuration`) that turns every `configuration['conditions'][*]` array back into a `ConditionInterface` via `coreshop.factory.rule_condition`, recursively.
  - Defensive (dependent: Component/Rule): make `NestedConditionChecker` accept both `ConditionInterface` and `array{type, configuration}` entries and build the condition on the fly, so already damaged rows keep working.
  - Long term: store nested children as plain arrays only (no objects in `configuration`), together with the `array` → `json` migration in TODO-3 **I-03**.
  - Add a regression test: `marshalVersion()` → `unmarshalVersion()` → `save()` → price calculation for a product with a `nested` specific price rule (TODO-3 **I-12**).
